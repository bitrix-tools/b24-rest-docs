# Установка и использование B24GoSDK

{% note tip "" %}

Выберите инструмент для разработки с AI-агентом:

- используйте [Битрикс24 Вайбкод](../../ai-tools/vibecode.md), чтобы создать приложение для Битрикс24 по описанию задачи без знания языков программирования. Агент напишет код и разместит приложение на сервере без ручной настройки хостинга
- используйте [MCP-сервер](../../ai-tools/mcp.md), чтобы разрабатывать интеграцию через REST API в своем проекте. Агент будет обращаться к официальной REST-документации

{% endnote %}

[B24GoSDK](https://github.com/bitrix24/b24gosdk) — официальный Go SDK для REST API Битрикс24. Он берет на себя авторизацию, повторы при отказах, обход списков и разбор ответов, а метод REST вызывается по имени.

SDK не содержит оберток на отдельные методы. Это сделано намеренно: метод, который Битрикс24 выпустил сегодня, доступен в SDK сегодня же, и ничего не нужно обновлять или генерировать заново, когда API растет.

Используйте B24GoSDK:

- если разрабатываете интеграцию, приложение или фоновый сервис на Go,
- нужна авторизация через [входящие вебхуки](../../local-integrations/local-webhooks.md) или [OAuth-протокол](../../settings/oauth/index.md),
- нужны [пакетные запросы](../../settings/how-to-call-rest-api/batch.md) и выгрузка больших списков,
- важно предсказуемое поведение при обрывах связи и превышении лимитов.

B24GoSDK поддерживает:

1. Авторизацию через [входящие вебхуки](../../local-integrations/local-webhooks.md) и [OAuth-протокол](../../settings/oauth/index.md) с автоматическим продлением токена;
2. Универсальный вызов любого метода REST по имени;
3. [Пакетные запросы](../../settings/how-to-call-rest-api/batch.md) с цепочками `$result` и разбиением на части;
4. Обход списков по курсору сервера и по идентификатору — для больших выгрузок;
5. Разбор ответов: идентификаторы в обоих форматах, снятие обёрток, определение формы значения;
6. Разбор данных, которые Битрикс24 передает приложению: события установки и POST-данные страницы приложения.

Требуется Go 1.21 или выше. Внешних зависимостей у SDK нет.

## Чем этот SDK отличается от остальных

Прочитайте этот раздел, если вы уже работали с B24PhpSDK, B24PySDK или
B24JsSDK. Рабочий процесс здесь другой, и примеры на этой странице выглядят
иначе не случайно.

| | B24PhpSDK, B24PySDK | B24GoSDK |
|---|---|---|
| Вызов метода | обертка: `deal()->add(...)` | по имени: `Call(ctx, "crm.deal.add", …)` |
| Имя и параметры метода | подсказывает IDE | берете из документации REST |
| Ответ | типизированный объект | сырой JSON, структуру объявляете вы |
| Новый метод портала | ждете обновления SDK | доступен сразу |

Плата понятная: **автодополнения по методам REST нет**, потому что имя метода —
обычная строка. Взамен доступен весь REST целиком, включая метод, который
Битрикс24 выпустил сегодня, а SDK не отстает от API и не требует регенерации.

## Как писать интеграцию

Порядок, который заменяет автодополнение.

### 1. Найдите метод в документации

Имена методов и их параметры в SDK не хранятся, и **выдумывать их нельзя**:
это `crm.deal.add`, а не `crm.deals.create`. Точные имена, параметры и форма
ответа — в [справочнике REST API](../../api-reference/index.md).

Форма ответа — тоже факт документации, а не SDK: то, что `crm.deal.add`
отвечает голым идентификатором, а `crm.deal.update` — булевым значением,
написано там, а не здесь.

### 2. Вызовите метод по имени

```go
res, err := client.Core().Call(ctx, "crm.deal.get",
    b24.Params{"id": 1}, b24.WithIdempotent())
```

### 3. Посмотрите, что портал прислал на самом деле

Этого шага нет в других SDK, и именно он заменяет подсказки IDE: про форму
ответа вам отвечает не редактор, а сам портал. В SDK для этого есть инструменты:

```go
// Какая это вообще форма: объект, массив, скаляр?
fmt.Println(b24.Result(res.Result).Kind())

// Какие поля реально пришли — в том написании, в котором их прислали.
if keys, ok := b24.Keys(res.Result); ok {
    fmt.Println(keys)
}
```

Шаг стоит одного запуска, а экономит час догадок. Портал переименовывает поля
между запросом и ответом, отдает идентификатор то числом, то строкой, а одно и
то же поле присылает объектом или массивом в зависимости от данных — увидеть
это глазами быстрее, чем вывести из документации.

### 4. Объявите структуру под ответ

Ровно те поля, которые вам нужны: лишние в ответе не мешают.

```go
type deal struct {
    ID    b24.ID `json:"ID"`
    Title string `json:"TITLE"`
    Stage string `json:"STAGE_ID"`
}

var d deal
if err := json.Unmarshal(res.Result, &d); err != nil {
    return err
}
```

Тип `b24.ID` вместо `int` — не перестраховка: идентификаторы приходят то числом,
то строкой в кавычках, иногда в рамках одного сценария.

### Если пишете с AI-агентом

Шаг 1 — ровно то, в чем чаще всего ошибается ИИ-агент: он уверенно придумывает
несуществующее имя метода. Поэтому вместе с задачей дайте агенту файл
[`llms.txt`](https://github.com/bitrix24/b24gosdk/blob/main/llms.txt) из корня
репозитория и [MCP-сервер документации](../../ai-tools/mcp.md): первый объясняет
устройство SDK, второй не дает выдумать метод.

## Установка

```bash
go get github.com/bitrix24/b24gosdk
```

Пакет называется `b24gosdk`, но в примерах он импортируется под коротким именем `b24`:

```go
import b24 "github.com/bitrix24/b24gosdk"
```

Репозиторий SDK доступен на GitHub: [bitrix24/b24gosdk](https://github.com/bitrix24/b24gosdk). Справочник API — на [pkg.go.dev](https://pkg.go.dev/github.com/bitrix24/b24gosdk).

## Использование со входящими вебхуками

Путь входящего вебхука — это секрет, дающий полный доступ к порталу. Читайте его из переменной окружения и не записывайте в код и в логи:

```go
package main

import (
    "context"
    "encoding/json"
    "log"
    "os"

    b24 "github.com/bitrix24/b24gosdk"
)

func main() {
    client := b24.NewClient(os.Getenv("B24_WEBHOOK_URL"))

    res, err := client.Core().Call(context.Background(), "crm.deal.add", b24.Params{
        "fields": b24.Params{
            "TITLE":    "Новая сделка",
            "TYPE_ID":  "SALE",
            "STAGE_ID": "NEW",
        },
    })
    if err != nil {
        log.Fatal(err)
    }

    var dealID b24.ID
    if err := json.Unmarshal(res.Result, &dealID); err != nil {
        log.Fatal(err)
    }
    log.Println("создана сделка", dealID)
}
```

Один объект `Client` создается на портал и переиспользуется: он хранит HTTP-клиент и состояние токена. Не создавайте его на каждый вызов.

`b24.Params` — это короткое имя для `map[string]any`. Оно объявлено как псевдоним, поэтому обе записи взаимозаменяемы и их можно смешивать внутри одного литерала.

## Вызов методов

Метод REST вызывается по имени. `Call` возвращает конверт ответа целиком, `CallJSON` — только поле `result`, `CallMultipart` загружает файлы:

```go
res, err := client.Core().Call(ctx, "crm.deal.list", params)
// res.Result — данные, res.Total — сколько всего записей,
// res.Next — смещение следующей страницы (nil, когда данные закончились)

raw, err := client.Core().CallJSON(ctx, "crm.deal.get", b24.Params{"id": 1})
```

Ни один из этих вызовов не возвращает вашу структуру: ответ приходит как `json.RawMessage`, и разбираете его вы. Имена методов и их параметры SDK не проверяет и не перечисляет — берите их из [справочника REST API](../../api-reference/index.md).

## Разбор ответа

Четыре ситуации встречаются в ответах Битрикс24 достаточно часто, чтобы SDK помогал с ними.

**Идентификаторы приходят то числом, то строкой** — иногда в рамках одного сценария: `disk.*` отдает `"ID": 6687`, `tasks.*` — `"id": "3711"`. Поле типа `b24.ID` разбирает оба варианта, а обратно сериализуется числом:

```go
var task struct {
    ID    b24.ID `json:"id"`
    Title string `json:"title"`
}
err := json.Unmarshal(res.Result, &task)
```

**Многие методы заворачивают ответ в объект с одним ключом** — `tasks.*` отвечает объектом с ключом `task`, `catalog.*` — с ключом `products`. `Unwrap` снимает такую обертку, не заводя структуру ради одного поля:

```go
raw, ok := b24.Unwrap(res.Result, "task")
```

Ключи сравниваются точно. Если портал переименовал поле между запросом и ответом — в `select` уходит `UF_TASK_WEBDAV_FILES`, а в ответе приходит `ufTaskWebdavFiles` — используйте `UnwrapFold`, который игнорирует регистр и подчеркивания, или `Keys`, чтобы посмотреть, что реально пришло.

**Пустое поле** приходит как `null`, пустая строка, `false`, пустой массив или пустой объект — в зависимости от метода и типа поля. `b24.IsEmpty` покрывает все пять вариантов; числовой ноль пустым не считается.

**Одно и то же поле приходит разной формой**, и какая именно — зависит от данных, а не от метода: свойство товара с одним значением приезжает объектом, с несколькими — массивом таких же объектов. `Result.Kind` отвечает, что именно пришло, чтобы выбрать цель декодирования:

```go
switch b24.Result(raw).Kind() {
case b24.KindArray:
    err = json.Unmarshal(raw, &values)
case b24.KindObject:
    var one value
    err = json.Unmarshal(raw, &one)
    values = []value{one}
case b24.KindNull:
    values = nil
}
```

## Обход списков

`Pages` идет по курсору сервера: отправляет `start` и повторяет `next`, пока сервер его возвращает.

```go
p, err := client.Core().Pages("crm.deal.list", b24.Params{
    "select": []any{"ID", "TITLE"},
})
if err != nil {
    return err
}
for p.Next(ctx) {
    for _, row := range p.Rows() {
        var d Deal
        if err := json.Unmarshal(row, &d); err != nil {
            return err
        }
    }
}
return p.Err()
```

Проверяйте `Err` после цикла всегда. `Next` возвращает `false` и в конце списка, и при ошибке, поэтому оборвавшийся обход выглядит как завершившийся, и только `Err` отличает одно от другого.

Для больших выгрузок используйте `Scan`. Постраничный обход заставляет сервер отсчитывать все пропущенные строки, поэтому последние страницы длинного списка идут все медленнее. `Scan` идет по идентификатору — сортирует по нему и фильтрует по последнему увиденному, — поэтому каждая страница стоит одинаково:

```go
p, err := client.Core().Scan("crm.deal.list", nil)
```

Семейства с нестандартной формой ответа SDK знает: `crm.item.*` возвращает строки внутри ключа `items` и строчный `id`, `tasks.task.*` возвращает `id`, но сортирует по `ID`, `user` и `department` принимают `SORT` и `ORDER` верхнего уровня. Для остальных случаев есть `WithRowPath`, `WithIDField` и `WithCursorParam`.

Если метод игнорирует курсор, обход не зацикливается: он останавливается с ошибкой `ErrCursorStalled`, а не запрашивает одну и ту же страницу за счет лимитов портала.

Свежие записи первыми дает `WithDescending`. Не разворачивайте `Scan` вручную: он листает по идентификатору, и разворачивать нужно и сортировку, и границу фильтра — иначе обход получает пустую вторую страницу и сообщает о полной выгрузке, в которой лежит только первая страница.

```go
p, err := client.Core().Scan("crm.deal.list", nil,
    b24.WithDescending(),
    b24.WithCallOptions(b24.WithTimeout(30*time.Second)),
)
```

`WithCallOptions` передает настройки в каждый запрос обхода. Это единственный способ ограничить одну страницу: обход принимает один контекст на весь цикл, поэтому иначе выбор такой — дедлайн на всю выгрузку либо никакого ограничения на зависшую страницу.

## Пакетные запросы

Пакет тратит один токен лимита вместо одного на команду, поэтому пятьдесят создающих вызовов — это один запрос, а не пятьдесят.

```go
b := b24.NewBatch()
idUser, _ := b.Add("user.current", nil)
b.AddAs("deals", "crm.deal.list", b24.Params{"filter": b24.Params{">ID": 5}})

res, err := client.Core().CallBatch(ctx, b)
raw, err := res.Get(idUser)
```

Команды выполняются в порядке добавления, как бы они ни назывались. `Get` отдает сырой результат команды. Служебные `next` и `total` внутрь него не попадают: сервер выносит их в отдельные секции ответа, и SDK кладет их в `res.Next` и `res.Total` с ключом по идентификатору команды. Признак «есть еще страница» — это наличие ключа, а не значение: `next` со значением ноль это законное первое смещение.

Результат одной команды подставляется в параметры следующей через `Ref`:

```go
b := b24.NewBatch()
b.Halt = true

b.AddAs("c", "crm.contact.add", b24.Params{
    "fields": b24.Params{"NAME": "Анна"},
})
ref, err := b24.Ref("c")
if err != nil {
    return err
}
b.AddAs("note", "crm.timeline.comment.add", b24.Params{
    "fields": b24.Params{"ENTITY_ID": ref, "ENTITY_TYPE": "contact"},
})
```

Для цепочки поле `Halt` обязательно. Если команда-источник упала, ее подстановка не становится ошибкой — сервер подставляет неразрешенный текст как обычное значение, и следующая команда выполняется с испорченным параметром. `Halt` останавливает пакет вместо этого.

`CallBatch` не делит пакет: если команд больше пятидесяти, он вернет ошибку. Для неограниченного набора независимых команд используйте `CallBatchChunked` — он разбивает набор и склеивает результаты. Для цепочек он не годится: подстановка `$result` не переживает границу части.

Ошибка пакета — частичная. Сервер отвечает HTTP 200 и кладет неудачи отдельных команд в секцию ошибок, поэтому результат возвращается вместе с ошибкой, и выбрасывать его нельзя: повтор всего пакета переисполнил бы уже закоммиченные команды.

```go
res, err := client.Core().CallBatch(ctx, b)

var be *b24.BatchError
if errors.As(err, &be) {
    // be.Failed — что упало, res — все, что выполнилось.
    // Соберите новый пакет из be.Failed и повторите только его.
}
```

`res.Executed` отличает «команда выполнилась и упала» от «команда не выполнялась, потому что пакет остановился раньше».

## Телефоны и почта

CRM хранит их списком строк, и набор ключей в строке решает, что произойдет. Строки, которые вы не упомянули, остаются как были, поэтому удаление должно быть явным:

```go
"PHONE": []map[string]any{
    b24.MultifieldAdd("+7 900 000-00-00", "MOBILE"),
    b24.MultifieldSet(rowID, "+7 900 111-11-11"),
    b24.MultifieldDelete(rowID),
}
```

Строка без идентификатора всегда добавляет: повторно отправленный существующий телефон без его идентификатора создаст дубль, а не обновит запись.

## Файлы

Файлы едут в base64 внутри параметров запроса, отдельного помощника для этого не нужно:

```go
"fileContent": []string{name, base64.StdEncoding.EncodeToString(content)},
```

Это пара из имени файла и его содержимого. Для больших файлов вызовите `disk.folder.uploadfile` без `fileContent`, получите адрес загрузки и отправьте байты туда.

## Ошибки

Ошибку, о которой сообщил REST API, SDK возвращает как `*b24.APIError` с полями `Code`, `Description` и `HTTPStatus`. Сравнивайте код через `errors.Is`, а не строковым равенством: опечатка в литерале компилируется, запускается и молча уводит выполнение не в ту ветку.

```go
if errors.Is(err, b24.ErrMethodNotFound) {
    // метод не существует или недоступен на этом портале
}
if errors.Is(err, b24.Code("CREATE_DYNAMIC_TYPE_RESTRICTED")) {
    // любой код, для которого нет именованной константы
}
```

Сравнение регистронезависимо — портал шлет одни коды в верхнем регистре, другие в нижнем — и идет только по коду. Проверка по HTTP-статусу спутала бы разные ситуации: `OVERLOAD_LIMIT` и `QUERY_LIMIT_EXCEEDED` оба приезжают с кодом 503, но первое означает ручную блокировку, а второе — превышение частоты запросов.

Именованные константы есть для частых кодов: `ErrQueryLimitExceeded`, `ErrOperationTimeLimit`, `ErrExpiredToken`, `ErrInvalidToken`, `ErrInvalidGrant`, `ErrInsufficientScope`, `ErrMethodNotFound`, `ErrAccessDenied`, `ErrPaymentRequired`. Набор намеренно открытый: портал выпускает новые коды без предупреждения, и `b24.Code` покрывает любой из них.

### Повторы

Решение о повторе SDK принимает по вопросу «выполнился ли запрос», а не «временная ли ошибка».

- `QUERY_LIMIT_EXCEEDED` — это отказ до выполнения, поэтому такой вызов повторяется всегда: повтор ничего не задвоит.
- Сетевой сбой, таймаут, нечитаемое тело ответа, ошибка 5xx без кода — неоднозначны, запрос мог выполниться. По умолчанию они не повторяются, потому что повтор `crm.deal.add` создал бы вторую сделку.
- Если повторить вызов безопасно, скажите об этом явно:

```go
res, err := client.Core().Call(ctx, "crm.deal.get",
    b24.Params{"id": 42}, b24.WithIdempotent())
```

Передавайте `WithIdempotent` для чтения и для записи фиксированных значений. Не передавайте для методов создания и для обновлений, где новое значение вычисляется из старого.

Обход списков повторяет страницы сам: чтение безопасно повторять, и без этого один обрыв связи на сороковой странице бросал бы весь обход. Пакет не повторяется никогда: в нем могут быть уже закоммиченные команды.

## Приложения и OAuth-протокол

Access-токен живет около часа. Чтобы SDK продлевал его сам, передайте `WithTokenRefresher`. Готовая реализация — `oauth.NewRefresher`: она хранит актуальный refresh-токен, потому что сервер авторизации выдает новую пару при каждом продлении, и отдает новую пару в функцию, где ее нужно сохранить:

```go
import (
    b24 "github.com/bitrix24/b24gosdk"
    "github.com/bitrix24/b24gosdk/oauth"
)

oauthClient := oauth.NewClient(clientID, clientSecret)
url := oauthClient.AuthorizeURL("example.bitrix24.com", state, redirectURI)

resp, err := oauthClient.ExchangeCode(ctx, code)

refresher := oauth.NewRefresher(oauthClient, resp.RefreshToken,
    func(t oauth.TokenResponse) {
        storeTokens(t.AccessToken, t.RefreshToken)
    })

client := b24.NewOAuthClient(resp.ClientEndpoint, resp.AccessToken,
    b24.WithTokenRefresher(refresher.Refresh))
```

Продление не выполняется по таймеру: сервер авторизации вызывается только тогда, когда токен действительно истек. Одновременные запросы делят одно продление, а неудачное продление не повторяется для того же токена.

Данные, которые Битрикс24 передает приложению, разбирают отдельные функции. Событие установки приходит в формате формы, а не JSON:

```go
ev, err := b24.ParseOnAppInstallRequest(r)
// ev.Auth содержит AccessToken, RefreshToken, ExpiresIn, Scope,
// MemberID и ApplicationToken — сохраните их, это единственный момент,
// когда они приходят

ok := ev.Auth.VerifyApplicationToken(stored)
```

`VerifyApplicationToken` сравнивает значения за постоянное время. Проверяйте токен до того, как что-то делать с данными события.

POST-данные страницы приложения разбирает `ParseAppRequest`, а клиент из них создается одной функцией:

```go
req, err := b24.ParseAppRequest(r)
client, err := b24.NewClientFromAppRequest(req)
```

## Тестирование интеграции без портала

Пакет `b24test` дает фейковый портал и заготовки ответов, чтобы код интеграции проверялся без сети и без настоящего портала:

```go
p := b24test.NewPortal(t)
p.On("crm.deal.get", b24test.Result(map[string]any{"ID": "42", "TITLE": "Сделка"}))
p.OnError("crm.deal.add", "QUERY_LIMIT_EXCEEDED", "слишком часто")

client := p.Client()
// ... выполните код, который тестируете, затем проверьте, что он отправил:
p.CallsTo("crm.deal.get")[0].Params["id"]
```

Не пишите заглушки на типы SDK вручную. В интеграции с Битрикс24 ломается провод: идентификатор, который приехал строкой; список, спрятанный под ключом; ошибка лимита с HTTP-статусом 503; пакет, где одна команда упала внутри ответа 200. Заглушка воспроизводит ваши представления, а `b24test` — то, как выглядят байты с портала.

Значения в заготовках подставные, из примеров документации. Заготовки попадают в репозиторий, и настоящий токен в них означал бы утекший доступ.

## Разработка с AI-агентом

В корне репозитория лежит файл [`llms.txt`](https://github.com/bitrix24/b24gosdk/blob/main/llms.txt) — точка входа для AI-агента, который пишет интеграцию. Он написан для агента, а не для человека, и содержит то, что агент чаще всего делает неправильно: имена методов REST в SDK не хранятся и их нельзя выдумывать, семь особенностей именно этого SDK и ловушки, которые стоят данных, а не ошибки.

Передайте этот файл агенту вместе с задачей.
