# BIconnector: обзор методов

{% note tip "" %}

Выберите инструмент для разработки с AI-агентом:

- используйте [Битрикс24 Вайбкод](../../ai-tools/vibecode.md), чтобы создать приложение для Битрикс24 по описанию задачи без знания языков программирования. Агент напишет код и разместит приложение на сервере без ручной настройки хостинга
- используйте [MCP-сервер](../../ai-tools/mcp.md), чтобы разрабатывать интеграцию через REST API в своем проекте. Агент будет обращаться к официальной REST-документации

{% endnote %}

BIconnector — это модуль Битрикс24 с методами для подключения внешних источников данных и их адаптации для раздела «Рабочее место аналитика».

Модуль объединяет три группы актуальных методов: коннекторы, источники и таблицы. Вместе они образуют цепочку работы с данными — от настройки подключения внешнего сервиса до получения набора данных для отчетов. Четвертая группа, `biconnector.dataset.*`, устарела — чем ее заменить, сказано ниже.

{% note warning "" %}

Методы работают только в контексте [приложения](../../settings/app-installation/index.md) и только с теми объектами, которые приложение создало само. При вызове вебхуком методы возвращают ошибку `ACCESS_DENIED`. Исключение — методы `*.fields`: они возвращают описание полей объекта и доступны вебхуку

{% endnote %}

## Коннекторы

Коннектор задает правила интеграции с внешней системой. Он хранит адреса четырех обязательных эндпоинтов: проверка подключения, список таблиц, описание таблицы и получение данных. Также коннектор объявляет, какие параметры авторизации пользователь заполнит при создании источника.

Коннектор не хранит значения параметров авторизации — их задает источник. Поэтому один коннектор можно использовать для нескольких источников: например, для тестовой и рабочей базы, которые отдают данные через одни и те же эндпоинты, но с разными учетными данными.

Для работы с коннекторами используйте методы [biconnector.connector.*](./connector/index.md). Состав полей — в таблице [полей коннектора](./connector/index.md#fields).

## Источники

Источник — это рабочее подключение, созданное на основе коннектора.

Источник связан с коннектором через `connectorId` и хранит значения тех параметров авторизации, которые объявил коннектор. Состав параметров произвольный: коннектор сам решает, что запросить у пользователя — токен, логин с паролем или идентификатор рабочего пространства. Тип параметра коннектор объявляет значением `STRING` или `INT`.

Для работы с источниками используйте методы [biconnector.source.*](./source/index.md). Состав полей — в таблице [полей источника](./source/index.md#fields).

## Таблицы

Таблица — это описание набора данных, который приложение отдает в «Рабочее место аналитика».

Таблица связана с источником через `sourceId` и задает структуру данных для аналитики: какие колонки доступны, какие у них типы и какие из них видны в отчетах. Из одного источника можно создать несколько таблиц, чтобы использовать их в разных отчетах.

Для работы с таблицами используйте методы [biconnector.table.*](./table/index.md). Состав полей — в [описании полей таблицы](./table/index.md#table).

{% note info "" %}

Раньше эти же объекты создавало семейство `biconnector.dataset.*` — оно устарело. Если ваша интеграция его использует, сверьтесь с [таблицей соответствия методов](./dataset/index.md#replacement): у пяти методов из семи меняется только имя в вызове, а `dataset.add` и `dataset.delete` ведут себя иначе — расхождения разобраны там же

{% endnote %}

## Как начать работу

1. Разместите на своей стороне [четыре эндпоинта](./connector/index.md#endpoints): проверка подключения, список таблиц, описание таблицы и получение данных. Без них коннектор создать нельзя — адреса всех четырех обязательны.
2. Создайте коннектор методом [biconnector.connector.add](./connector/biconnector-connector-add.md): передайте название, логотип, адреса всех четырех эндпоинтов и коды параметров авторизации — это обязательные поля. В ответе придет `id` коннектора.
3. Создайте источник методом [biconnector.source.add](./source/biconnector-source-add.md): передайте `connectorId`, название и значения параметров авторизации. При создании Битрикс24 сразу обратится к эндпоинту проверки подключения — если он не ответит, источник не создастся.
4. Создайте таблицу методом [biconnector.table.add](./table/biconnector-table-add.md). Обязательных полей пять: `sourceId` источника, `name`, `externalName`, `externalCode` и состав колонок `fields`. Позже состав колонок меняется методом [biconnector.table.fields.update](./table/biconnector-table-fields-update.md).

## Как проверить состав полей

Методы `*.fields` возвращают схему объекта: имя поля, тип, обязательность и признаки «только для чтения», «неизменяемое», «множественное». Схема одинакова в любом Битрикс24 и не зависит от того, что вы уже создали, — по ней сверяют состав полей, а не текущие данные:

- [biconnector.connector.fields](./connector/biconnector-connector-fields.md) — поля коннектора
- [biconnector.source.fields](./source/biconnector-source-fields.md) — поля источника
- [biconnector.table.fields](./table/biconnector-table-fields.md) — поля таблицы

В ответе есть и поля только для чтения — передать их в `add` или `update` нельзя.

## Формат ответа {#responses}

Формы успешного ответа совпадают у всех трех групп методов, кроме одного случая:

#|
|| **Методы** | **Что приходит** ||
|| `*.add` | `result.id` — идентификатор созданного объекта ||
|| `*.get` | `result.item` — объект целиком. Исключение — [biconnector.source.get](./source/biconnector-source-get.md): собственные поля источника лежат во вложенном объекте `result.item.connection` ||
|| `*.list` | `result` — массив объектов без обертки ||
|| `*.update`, `*.delete`, `*.fields.update` | `result: true` ||
|| `*.fields` | `result.fields` — массив с описанием полей ||
|#

Состав объекта может пополняться: в ответах появляются поля соседних сценариев, например параметры разбора CSV у таблицы. Игнорируйте незнакомые ключи, а не считайте их ошибкой.

### Ошибки приходят внутри result {#errors}

{% note warning "" %}

Методы раздела возвращают ошибку **внутри поля `result`** и с HTTP-статусом 200 — не так, как остальные методы REST API Битрикс24

{% endnote %}

```json
{
    "result": {
        "error": {
            "error": "ACCESS_DENIED",
            "error_description": "Access denied."
        }
    }
}
```

Блок `time` в таком ответе приходит как обычно — по нему отличить ошибку от успеха нельзя. Проверяйте наличие ошибки в `result.error`, а не в корне ответа. Готовые обертки SDK разбирают только верхний уровень, поэтому такой ответ они считают успешным: вызов вернет объект с полем `error` вместо ожидаемых данных.

Из этого правила есть одно исключение. Если в параметре `order` списочных методов передать направление сортировки, отличное от `ASC` и `DESC`, ответ формирует не модуль, а уровень ниже: запрос завершается HTTP-статусом 400, а ошибка `ERROR_ARGUMENT` лежит в корне ответа, а не в `result`.

Коды ошибок, общие для всего раздела:

#|
|| **Код** | **Когда приходит** ||
|| `ACCESS_DENIED` | Причин три: у пользователя нет одного из двух прав; метод вызван вебхуком; метод вызван вне контекста приложения. Методы `*.fields` вебхуку доступны, для них остается только причина с правами ||
|| `CONNECTOR_NOT_FOUND`, `SOURCE_NOT_FOUND`, `DATASET_NOT_FOUND` | Объекта нет или он принадлежит другому приложению. Чужие объекты приложение не видит, поэтому «нет доступа» приходит как «не найдено». Про ненайденную таблицу методы `biconnector.table.*` тоже сообщают кодом `DATASET_NOT_FOUND`: отдельного `TABLE_NOT_FOUND` в модуле нет ||
|| Коды семейства `VALIDATION_` | Не заполнено обязательное поле, передано поле только для чтения или неизменяемое либо указан неизвестный параметр — это проверяют `add`, `update` и `fields.update`. У методов `list` свои коды: неверный тип `select`, `filter` или `order` и недопустимое в них поле ||
|| `BX_ERROR` | Общая ошибка модуля. Приходит, например, когда источник нельзя удалить из-за связанных с ним таблиц. У коннектора тот же случай приходит отдельным кодом `CONNECTOR_DELETE_RESTRICTED` ||
|#

Коды, специфичные для метода, перечислены на его странице.

### Постраничная навигация в методах list {#pagination}

Размер страницы фиксированный — 50 элементов. Номер страницы передается в необязательном параметре `page` типа [`integer`](../data-types.md), нумерация начинается с единицы, значение по умолчанию — 1. Параметр `start`, общий для большинства методов REST API, здесь не работает и молча игнорируется.

Методы не возвращают ни общее количество элементов, ни ссылку на следующую страницу, поэтому автоматический обход списков неприменим. Признак конца выборки один: страница вернулась короче 50 элементов.
