Почтовый сервис — это запись в реестре Битрикс24 с параметрами почтового сервера: названием, адресом и портом IMAP-сервера, признаком защищенного подключения, логотипом и ссылкой на веб-интерфейс. Пользователь выбирает сервис из этого реестра, когда подключает свой почтовый ящик. В Битрикс24 уже есть сервисы Яндекс, Mail.ru, Gmail и другие, а методы раздела позволяют дополнить реестр своим сервисом.

Реестр хранится отдельно для каждого сайта, поэтому методы работают только с сервисами текущего сайта.

## Как начать работу

1. Посмотрите, какие сервисы уже есть в Битрикс24, методом [mailservice.list](./mailservice-list.md)
2. Если нужного сервиса нет, создайте его методом [mailservice.add](./mailservice-add.md). Метод возвращает `ID` нового сервиса — сохраните это значение
3. Измените параметры сервиса методом [mailservice.update](./mailservice-update.md) или удалите сервис методом [mailservice.delete](./mailservice-delete.md)
4. Получить параметры одного сервиса по `ID` можно методом [mailservice.get](./mailservice-get.md)

`mailservice.list` отдает только активные сервисы. `mailservice.get` вернет и неактивный, но для этого нужно знать его `ID`: других способов получить `ID` неактивного сервиса через REST нет.

## Связь с другими объектами

Почтовый сервис связан с почтовыми ящиками пользователей, с сайтом и с файлом логотипа.

**Почтовый ящик.** Поля сервиса применяются к уже подключенным ящикам, которыми управляют методы раздела [Почтовые ящики](../mail/mailbox/index.md). Поля `NAME`, `ACTIVE`, `SERVER`, `PORT`, `ENCRYPTION` и `LINK`, измененные методом [mailservice.update](./mailservice-update.md), переносятся на все привязанные ящики. Логотип `ICON` и сортировка `SORT` на ящики не влияют. Если перевести IMAP-сервис в `ACTIVE: N` или удалить его методом [mailservice.delete](./mailservice-delete.md), привязанные ящики переходят на пустой сервис того же сайта — активный сервис с незаполненными `SERVER`, `PORT`, `ENCRYPTION` и `LINK`. Если такого сервиса нет, ящики отключаются. При переезде на пустой сервис остальные поля, переданные в том же вызове `mailservice.update`, на ящики не переносятся. У встроенных сервисов других типов удаление всегда отключает привязанные ящики.

**Сайт.** Сервис принадлежит сайту, идентификатор которого возвращается в поле `SITE_ID`. Изменить привязку через REST нельзя.

**Файл.** Логотип сервиса передают в поле `ICON` файлом или идентификатором существующего файла.

## Поля почтового сервиса

Состав полей сервиса описан в [объекте ответа](./mailservice-get.md#mail-service) метода `mailservice.get`. Метод [mailservice.list](./mailservice-list.md#mail-services) возвращает массив таких же объектов. Типы и допустимые значения записываемых полей приведены в параметрах методов [mailservice.add](./mailservice-add.md) и [mailservice.update](./mailservice-update.md), значения по умолчанию — в параметрах `mailservice.add`. Управлять выдачей параметрами нельзя: `mailservice.list` и `mailservice.fields` вызывают без параметров, фильтрации и постраничной навигации в разделе нет. Список сервисов приходит в порядке поля `SORT`, а при равных значениях — по `NAME`.

Сквозные правила раздела:

- имена полей записываются в верхнем регистре, логические значения передаются строками `Y` и `N`
- при создании обязательно поле `NAME`, методам `get`, `update` и `delete` нужен `ID`. Методы `update` и `delete` возвращают `true`
- задать при создании и изменении можно только поля `NAME`, `ACTIVE`, `SERVER`, `PORT`, `ENCRYPTION`, `LINK`, `ICON` и `SORT`. Все остальные поля объекта ответа, включая `ID`, `SITE_ID`, `UPLOAD_OUTGOING` и поля SMTP-сервера `SMTP_*`, через REST задать нельзя
- через REST создается только IMAP-сервис: тип подключения задает система, в ответе он не возвращается
- метод [mailservice.update](./mailservice-update.md) игнорирует поля с пустым значением, поэтому очистить `LINK` или `SERVER` этим методом не получится, а `PORT: 0` и `SORT: 0` не запишутся. В [mailservice.add](./mailservice-add.md) правило другое: пустые `ACTIVE` и `SORT` заменяются значениями по умолчанию
- метод [mailservice.fields](./mailservice-fields.md) возвращает названия полей для подписей в интерфейсе, но не все поля объекта: полей SMTP и `UPLOAD_OUTGOING` в его ответе нет — состав смотрите в [объекте ответа](./mailservice-fields.md#fields-map) этого метода
- в ответе поле `ICON` приходит путем к изображению, а не идентификатором файла, поэтому обратно его значение передать нельзя. Если логотип не задан и название сервиса не совпадает с одним из встроенных, в ответе придет `null`

## Кто может работать с почтовыми сервисами

- создавать, изменять и удалять почтовый сервис может только администратор
- получать сервис по идентификатору, список сервисов и названия полей может любой пользователь

## Ошибки раздела

Собственные ошибки методов раздела приходят с HTTP-статусом 400 и с одним кодом `ERROR_CORE`. Причина отличается только текстом в `error_description`, поэтому различать такие случаи по коду ошибки нельзя — разбирайте описание. Текст зависит от языка интерфейса, опираться на него как на стабильный контракт не стоит. Типовые причины:

- недостаточно прав
- не передан обязательный параметр `ID` или `NAME`
- сервис с указанным `ID` не найден
- передано недопустимое значение поля
- на сайте нет ни одного активного сервиса — в этом случае [mailservice.list](./mailservice-list.md) вернет ошибку, а не пустой массив

Кроме собственных ошибок раздела приходят общие системные ошибки REST: истекший токен, нехватка `scope`, превышение лимитов. Они описаны в статье [Коды ошибок](../../error-codes.md). Перечень ошибок каждого метода приведен на его странице.
