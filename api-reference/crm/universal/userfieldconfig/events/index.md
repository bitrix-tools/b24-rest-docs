# Обзор событий при работе с настройками пользовательских полей

{% note tip "" %}

Выберите инструмент для разработки с AI-агентом:

- используйте [Битрикс24 Вайбкод](../../../../../ai-tools/vibecode.md), чтобы создать приложение для Битрикс24 по описанию задачи без знания языков программирования. Агент напишет код и разместит приложение на сервере без ручной настройки хостинга
- используйте [MCP-сервер](../../../../../ai-tools/mcp.md), чтобы разрабатывать интеграцию через REST API в своем проекте. Агент будет обращаться к официальной REST-документации

{% endnote %}

События дают возможность приложениям реагировать на изменения практически в реальном времени: получать уведомления о добавлении, изменении и удалении настроек пользовательских полей.

Подробно работа с событиями описана в статье [Концепция и преимущества обработки событий](../../../../events/index.md).

> Быстрый переход: [все события](#all-events)

## Как получать события

Подписаться на события настроек пользовательских полей можно через:

- [исходящий вебхук](../../../../../local-integrations/local-webhooks.md)
- [приложение](../../../../../settings/app-installation/index.md) и метод [event.bind](../../../../events/event-bind.md)

Пример кода обработчика для события описан в статье [Как проверить свой обработчик для обработки событий Битрикс24](../../../../events/test-handler.md).

Регистр в имени события при подписке не важен: `event.bind` принимает и `onCrmTypeUserFieldAdd`, и `ONCRMTYPEUSERFIELDADD`. В ответах [event.get](../../../../events/event-get.md) и в поле `event` самого события имя всегда приходит заглавными буквами.

Событиям раздела нужен scope `crm` — их регистрирует модуль CRM. Методы `userfieldconfig.*` требуют другой набор: `userfieldconfig` и scope модуля из `moduleId`. Приложению, которое и подписывается на события, и читает настройки полей, нужны оба scope.

## Для каких объектов срабатывают события {#objects}

События срабатывают для пользовательских полей трех объектов CRM.

#|
|| **Объект** | **`ENTITY_ID` пользовательского поля** ||
|| Смарт-процесс | `CRM_{id}`, где `id` — ключ `id` из результата метода [crm.type.list](../../user-defined-object-types/crm-type-list.md). Это не `entityTypeId`: у смарт-процесса с `id = 13` и `entityTypeId = 156` значение будет `CRM_13` ||
|| Новый счет | `CRM_SMART_INVOICE` ||
|| Документ на подпись | `CRM_SMART_DOCUMENT` ||
|#

Для пользовательских полей других объектов и модулей события раздела не приходят:

- изменения полей в процессах Роботизации бизнеса с `moduleId=rpa` и в документах складского учета с `moduleId=catalog` события не отправляют
- для полей счетов старого образца события раздела тоже не приходят: у них свои события с кодами `onCrmInvoiceUserField*`

## Что приходит в обработчик

События передают в объекте `data.FIELDS` идентификатор пользовательского поля, объект, к которому оно относится, и его код:

```json
{
    "event": "ONCRMTYPEUSERFIELDUPDATE",
    "data": {
        "FIELDS": {
            "ID": "6977",
            "ENTITY_ID": "CRM_13",
            "FIELD_NAME": "UF_CRM_13_1742999523"
        }
    }
}
```

В примере показана только значимая часть запроса. Кроме `event` и `data`, обработчик получает еще три ключа верхнего уровня:

- `event_handler_id` — идентификатор обработчика события
- `ts` — дата и время отправки события из очереди
- `auth` — [параметры авторизации](./on-crm-type-user-field-add.md#auth) и данные о Битрикс24, на котором произошло событие

Полный payload со всеми ключами показан на страницах событий, например [onCrmTypeUserFieldAdd](./on-crm-type-user-field-add.md). Чтобы убедиться, что запрос пришел от Битрикс24, сверяйте `auth.application_token` и `auth.member_id` со значениями своего приложения.

Событие доставляется POST-запросом, поэтому значения внутри `data.FIELDS` приходят строками. Приводите `ID` к числу, если сравниваете его с идентификаторами из ответов методов.

Состав `FIELDS` одинаковый у всех четырех событий. Тип поля, его настройки и список значений в событии не передаются — запросите их методом [userfieldconfig.get](../userfieldconfig-get.md), передав пришедший `ID` вместе с `moduleId = crm`. Методу нужен scope `userfieldconfig` в дополнение к scope `crm`, с которым приложение подписывается на событие.

После события `onCrmTypeUserFieldDelete` метод вернет ошибку с пустым кодом и текстом `Вы не можете просматривать настройки пользовательских полей`. Такую же ошибку он возвращает при нехватке прав на просмотр поля, поэтому отличить удаленное поле от отказа по правам по коду ошибки нельзя. Остальные ошибки разобраны на странице [userfieldconfig.get](../userfieldconfig-get.md).

### Какие события приходят вместе {#pairs}

Одно действие с полем списочного типа `enumeration` отправляет одно или два события:

#|
|| **Что произошло** | **Какие события придут** ||
|| Создали поле со списком значений | `onCrmTypeUserFieldAdd` и `onCrmTypeUserFieldSetEnumValues` ||
|| Изменили настройки поля вместе со списком значений | `onCrmTypeUserFieldUpdate` и `onCrmTypeUserFieldSetEnumValues` ||
|| Изменили только набор значений | `onCrmTypeUserFieldSetEnumValues` ||
|| Изменили настройки поля любого другого типа | `onCrmTypeUserFieldUpdate` ||
|#

Отличить эти случаи по содержимому `data` нельзя — во всех событиях приходят одни и те же три ключа. Если обработчик подписан и на `onCrmTypeUserFieldUpdate`, и на `onCrmTypeUserFieldSetEnumValues`, предусмотрите защиту от повторной обработки одного и того же `ID`.

События приходят только на действия с самим полем. Когда удаляют смарт-процесс целиком, его пользовательские поля тоже пропадают, но `onCrmTypeUserFieldDelete` по ним не отправляется — такие случаи отслеживайте событием [onCrmTypeDelete](../../events/type/on-crm-type-delete.md).
