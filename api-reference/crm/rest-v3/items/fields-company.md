{% note info "" %}

Поля относятся к методам REST 3.0. Особенности вызова и формат ответа новой версии API описаны в [обзоре REST 3.0](../../../rest-v3.md).

{% endnote %}

Поля компании возвращают методы [crm.company.get](./crm-entity-get-rest-v3.md) и [crm.company.list](./crm-entity-list-rest-v3.md), а принимают методы [crm.company.add](./crm-entity-add-rest-v3.md) и [crm.company.update](./crm-entity-update-rest-v3.md). Значения множественных полей по одному добавляют и удаляют методы [crm.company.addfieldvalue](./crm-entity-add-field-value-rest-v3.md) и [crm.company.deletefieldvalue](./crm-entity-delete-field-value-rest-v3.md). Список полей с признаками возвращает метод [crm.company.field.list](../fields/crm-entity-field-list-rest-v3.md).

Методы `crm.company.*` работают только с компаниями клиентов. Компании из справочника «Мои компании» они не находят: `crm.company.get` вернет ошибку «Запись с ID = `…` не найдена», а `crm.company.list` их не покажет. Для своих компаний используйте методы `crm.mycompany.*`, их поля описаны в статье [Поля моей компании в REST 3.0](./fields-my-company.md).

Часть полей существует в двух видах: как идентификатор и как связанный объект, например `assignedById` и `assignedBy`. Идентификатор можно передать при записи, а связанный объект — только запросить в `select`.

## Какие поля принимают и возвращают методы {#methods}

#|
|| **Метод** | **Принимает** | **Возвращает** ||
|| [crm.company.add](./crm-entity-add-rest-v3.md) | Поля таблицы [Объект компании](#item), которые можно изменять, и пользовательские поля. Обязательно поле `title`, иначе метод вернет ошибку «Не заполнено обязательное поле "title"» | Идентификатор созданной компании `id` ||
|| [crm.company.update](./crm-entity-update-rest-v3.md) | `id` компании и те же поля, что `add`. Поля, которых нет в `fields`, сохраняют текущие значения | Признак успеха `true` ||
|| [crm.company.get](./crm-entity-get-rest-v3.md) | `id` компании и `select` | Без `select` — только `id`. С `select` — только перечисленные поля, `id` не добавляется автоматически. Связанный объект целиком, например `assignedBy`, возвращает все свои поля, а путь через точку, например `assignedBy.firstName`, — только выбранные. Подробнее — в разделе [Связанные объекты](#relations) ||
|| [crm.company.list](./crm-entity-list-rest-v3.md) | `select`, `filter`, `order`, `pagination` | Без `select` — только `id` каждой компании. Поля и связанные объекты запрашиваются в `select` так же, как в `get` ||
|| [crm.company.addfieldvalue](./crm-entity-add-field-value-rest-v3.md), [crm.company.deletefieldvalue](./crm-entity-delete-field-value-rest-v3.md) | `id` компании, имя множественного поля `fieldName` и значение `value`. Подходят поля `phone`, `email`, `web`, `im`, `contactsId`, `observersId` и множественные пользовательские поля. Для других полей метод вернет ошибку «The field is not supported.» | Признак успеха `true` ||
|#

Поля с пометкой «только чтение» методы `add` и `update` не принимают и возвращают ошибку `BITRIX_REST_V3_EXCEPTION_VALIDATION_DTOVALIDATIONEXCEPTION` с текстом «Поле "contactId" не доступно к заполнению». Связанные объекты, например `contacts` и `assignedBy`, тоже только для чтения: для записи передавайте идентификатор — `contactsId`, `assignedById`.

Поля со значениями из справочников метод проверяет при записи. Если значения нет в справочнике, метод вернет ошибку «Значение поля не содержится в списке допустимых значений». Для типа компании, сферы деятельности, количества сотрудников и валюты в тексте ошибки перечислены допустимые значения.

Логические поля принимают и возвращают `true` или `false`. Значения `Y`, `N`, `1` и `0` не подходят: метод вернет ошибку «В поле `opened` требуется тип данных `bool` для такого запроса».

Поля типа `datetime` возвращаются в формате ISO 8601, например `2026-11-03T14:42:01+03:00`. В фильтре по полю `datetime` тоже передавайте дату со временем.

Фильтровать и сортировать можно только по полям, у которых это указано в описании. На другие поля метод `list` вернет ошибку «требуется наличие атрибута `Filterable`» или «`Sortable`». Через точку можно фильтровать по полям связанных элементов CRM, значений телефона, почты, сайта и мессенджера, объектов `utm` и `lastCommunication`, например `["contact.name", "=", "Иван"]` или `["phone.value", "=", "+79990000001"]`. По полям сотрудников и справочников, например `assignedBy.id` или `industry.name`, фильтр не работает: метод вернет ошибку `BITRIX_REST_V3_EXCEPTION_INVALIDFILTEREXCEPTION`. Формат фильтра описан на странице [crm.<тип>.list](./crm-entity-list-rest-v3.md) и в статье [Обзор REST API 3.0](../../../rest-v3.md#filter).

|| **valueTypeId**
[`string`](../../../data-types.md) | Тип значения, например `WORK` или `MOBILE`. Обязательное поле при записи. Допустимые типы для каждого поля возвращают методы [crm.dictionary.phonetype.list, crm.dictionary.emailtype.list, crm.dictionary.webtype.list и crm.dictionary.imtype.list](../dictionaries/crm-dictionary-list-rest-v3.md) ||
|| **valueType**
[`object`](../../../data-types.md) | Тип значения с названием: `id`, `name` — полное название, например `Рабочий телефон`, `nameShort` — краткое, например `Рабочий`. Только чтение ||
|| **value**
[`string`](../../../data-types.md) | Значение: номер телефона, адрес почты, адрес сайта или идентификатор в мессенджере. Обязательное поле при записи ||
|#

При записи передавайте массив объектов с полями `valueTypeId` и `value`:

```json
{
    "phone": [
        {"valueTypeId": "WORK", "value": "+79990000001"},
        {"valueTypeId": "MOBILE", "value": "+79990000002"}
    ]
}
```

В ответе каждое значение приходит с `id` и объектом `valueType`:

```json
{
    "phone": [
        {
            "id": 8861,
            "valueTypeId": "WORK",
            "valueType": {
                "id": "WORK",
                "name": "Рабочий телефон",
                "nameShort": "Рабочий"
            },
            "value": "+79990000001"
        }
    ]
}
```

Как работает запись:

- `crm.company.update` заменяет все значения поля переданным массивом. Значения, которых нет в массиве, удаляются. Другие множественные поля, которых нет в `fields`, не меняются
- пустой массив, например `"phone": []`, удаляет все значения поля
- одно значение добавляет метод [crm.company.addfieldvalue](./crm-entity-add-field-value-rest-v3.md), удаляет — [crm.company.deletefieldvalue](./crm-entity-delete-field-value-rest-v3.md). В `value` передайте объект `{"valueTypeId": "WORK", "value": "+79990000001"}`. Если такое значение уже есть, `addfieldvalue` вернет ошибку «The field value already exists.»
- в одном поле может быть до 50 значений, во всех четырех полях вместе — до 100. При превышении метод вернет ошибку «Too many phone multifields.»

### Поля связей с другими типами {#related}

Поля `related<Код типа>Id` и `related<Код типа>` появляются, когда в Битрикс24 настроена связь, в которой компания подчинена смарт-процессу. Для каждого родительского смарт-процесса у компании есть пара полей:

- `related<Код типа>Id` — идентификатор родительского элемента, например `relatedSmartProcess177Id` для смарт-процесса с `entityTypeId = 177`
- `related<Код типа>` — родительский элемент как объект типа [элемент CRM](#crm-item), например `relatedSmartProcess177`

Название поля в ответе `crm.company.field.list` совпадает с названием родительского смарт-процесса, например «Закупка оборудования». Метод проверяет, что элемент с переданным идентификатором существует. Если элемента нет, метод вернет ошибку «Значение поля не содержится в списке допустимых значений».

Состав этих полей зависит от связей, настроенных в Битрикс24. Актуальный список возвращает метод [crm.company.field.list](../fields/crm-entity-field-list-rest-v3.md).

## Связанные объекты {#relations}

Связанный объект запрашивается в `select` по имени поля без суффикса `Id`: `assignedBy`, `industry`, `contacts`. Имя объекта целиком возвращает все его поля, путь через точку — только выбранные, например `["type.name", "assignedBy.firstName"]`. Путь поддерживает один уровень вложенности: `contact.createdBy.firstName` метод не примет.

Связанный элемент CRM — `contact`, `contacts`, `lead`, `related<Код типа>` — по имени целиком возвращает только `id`. Остальные поля элемента запрашивайте через точку. Через точку доступны поля из [объекта элемента CRM](#crm-item) и любые поля типа связанного элемента, например `["contacts.title", "contacts.phone", "contact.post"]`. Поля контакта описаны в статье [Поля контакта в REST 3.0](./fields-contact.md).

Если связь не заполнена, объект приходит как `null`, а массив объектов, например `observers` или `contacts`, — как пустой массив.

## Пользовательские поля {#userfields}

Пользовательские поля компании называются `UF_CRM_<код>`, например `UF_CRM_1687188367`. Их передают и запрашивают по имени так же, как стандартные поля. Список пользовательских полей компании возвращает метод [crm.company.field.custom.list](../fields/crm-entity-field-custom-list-rest-v3.md). Те же поля есть у моих компаний.

Значение поля типа «Деньги» передается объектом `{"sum": 150.5, "currencyId": "RUB"}`. Строка вида `150.5|RUB` не подходит: метод вернет ошибку «В поле `UF_CRM_…` требуется тип данных `MoneyDto` для такого запроса».

У каждого пользовательского поля есть парное поле `UF_CRM_…_data` — только для чтения, запрашивается в `select`. Оно содержит значение в нескольких представлениях:

- `value` — значение в том же формате, что в самом поле
- `rawValue` — значение в формате хранения, например `150.5|RUB` для поля «Деньги»
- `formattedValue` — значение для показа пользователю: `150.50 ₽` для денег, имя сотрудника для поля «Привязка к сотруднику»
- `extra` — дополнительные данные: для денег — `amount`, `currencyId` и `currencyFullName`, для сотрудника — поля объекта [сотрудника](#employee). Для строки, числа и даты — `null`

У множественного пользовательского поля `UF_CRM_…_data` — массив таких объектов.
