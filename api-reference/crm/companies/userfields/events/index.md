События дают возможность приложениям реагировать на изменения практически в реальном времени: получать уведомления о создании, обновлении или удалении пользовательских полей компании.

Подробно работа с событиями описана в статье [Концепция и преимущества обработки событий](../../../../events/index.md). Методы, которыми управляют самими полями, собраны в разделе [Пользовательские поля компаний](../index.md).

## Что приходит в обработчик

События сообщают об изменении структуры пользовательских полей, а не значений в карточках компаний. Во всех четырех событиях обработчик получает одинаковый набор данных в `data.FIELDS`:

```json
{
    "event": "ONCRMCOMPANYUSERFIELDUPDATE",
    "data": {
        "FIELDS": {
            "ID": "6979",
            "ENTITY_ID": "CRM_COMPANY",
            "FIELD_NAME": "UF_CRM_1743165530"
        }
    }
}
```

- `ID` — идентификатор пользовательского поля
- `ENTITY_ID` — идентификатор объекта, к которому относится поле. Для компаний это всегда `CRM_COMPANY`
- `FIELD_NAME` — код пользовательского поля

В примере показана значимая часть запроса. Полный payload с параметрами `event_handler_id`, `ts` и `auth` приведен на страницах отдельных событий, например [onCrmCompanyUserFieldUpdate](./on-crm-company-user-field-update.md).

Тип поля, его настройки и значения списка в событии не передаются. Различайте события по коду в поле `event`, а не по составу `data.FIELDS`.

## Как обработать событие

1. Определите по полю `event`, какое изменение произошло
2. Для событий добавления, обновления и изменения значений списка передайте полученный `ID` в метод [crm.company.userfield.get](../crm-company-userfield-get.md), чтобы запросить актуальные свойства поля
3. Для события удаления используйте данные из `data.FIELDS` и сведения, которые интеграция сохранила ранее. После удаления поле уже недоступно через REST
