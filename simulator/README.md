# Симулятор REST API

Виджет «Попробовать метод» на страницах документации: форма собирается из
машиночитаемой схемы метода, вызов проверяется на корректность, read-методы
исполняются на встроенном тестовом датасете.

Симулятор **не делает реальных вызовов** и **не принимает секреты**. Ответ по
форме повторяет реальный REST API (`result` / `total` / `next` / `time`,
ошибки — `error` / `error_description`), метаданные симуляции лежат в
отдельном ключе `simulator`. Код, отлаженный здесь, переносится на реальный
портал заменой адреса и авторизации.

Схемы, датасет и виджет работают статикой, без бэкенда. Отдельно есть
HTTP-endpoint `/ai/v1/*` для ИИ-агентов — он использует те же артефакты.

## Состав

```
simulator/
  lib/yfm-table.js       разбор YFM-таблиц (#| ... |#), включая вложенные
  lib/build-spec.js      страница документации → схема метода
  lib/core.js            валидация + исполнение read-методов (браузер и Node)
  lib/config.js          пилотные разделы и список исполняемых методов
  widget/widget.js       виджет на компонентах документации
  widget/widget.css      только раскладка
  generate-spec.js       схемы → _assets/simulator/spec/
  generate-fixtures.js   датасет → _assets/simulator/fixtures/
  build.js               всё сразу + копирование runtime в _assets
  server.js              HTTP-endpoint /ai/v1/* для агентов
  check-examples.js      сверка примеров документации со схемами
  examples-baseline.json известные расхождения примеров
  test.js                тесты ядра
  test-server.js         тесты endpoint
```

Сборка кладёт результат в `_assets/simulator/` — этот каталог коммитится,
потому что сайт собирается статикой и отдельного шага сборки ассетов в
пайплайне документации нет.

## Команды

```bash
node simulator/build.js                       # схемы + датасет + runtime
node simulator/build.js --date=2026-08-14     # датасет на фиксированную дату
node simulator/generate-spec.js --lint        # отчёт парсера без записи файлов

node simulator/test.js                        # тесты ядра
node simulator/test-server.js                 # тесты endpoint
node simulator/check-examples.js              # сверка примеров документации
node simulator/check-examples.js --strict     # для CI: падает на новых расхождениях
node simulator/check-examples.js --baseline   # перезаписать список известных

node simulator/server.js --port=8080          # поднять /ai/v1/*
```

После правок страниц документации схемы нужно пересобрать: `node
simulator/build.js`, иначе виджет останется на старом контракте.

## Схема метода

Формат версионируется полем `$v`. Поле `source.file` связывает схему со
страницей — по нему отлаживается парсер.

Обязательность параметра трёхзначная: `true`, `false` и `"unknown"`.
`"unknown"` означает, что на странице не применено соглашение о звёздочке
(`**ИМЯ***` и сноска `_includes/required.md`) — тогда симулятор не может
проверить обязательность и выдаёт предупреждение `required_unknown` вместо
молчаливого «валидно». Сейчас таких параметров около 20% пилота.

Поле `confidence` пока всегда `parsed` — схема выведена из текста
документации и не сверена с реальным порталом. Значения `reviewed` и
`verified` зарезервированы под ручную вычитку и сверку с ответами портала.

Списочным и get-методам добавляется `entityFields` — состав полей сущности. Он
собирается из подтаблицы «Параметр fields» соответствующего `*.add`, страницы
справочника полей (для задач — `api-reference/tasks/fields.md`) и ключей примера
ответа. По нему проверяются имена в `filter`, `order` и `select`: имена
сравниваются без регистра и подчёркиваний, потому что в задачах фильтр пишется
`RESPONSIBLE_ID`, а поле называется `responsibleId`. Несовпадение даёт
предупреждение с подсказкой, а не ошибку — справочник полей может быть неполным.

## Типы

Документация называет ассоциативный массив то `array`, то `object`, а `char`
ставит и у флагов `Y`/`N`, и у коротких строк. Валидатор считает `array` и
`object` взаимозаменяемыми и не требует от `char` строго `Y`/`N`: ложная ошибка
в виджете хуже пропущенной.

## Сверка примеров документации

`check-examples.js` достаёт тела запросов из cURL-примеров на страницах методов и
прогоняет через валидатор. Расхождений на старте много, поэтому известные
заморожены в `examples-baseline.json`, а `--strict` падает только на новых.
Примеры с подстановками оболочки (`$(date ...)`) пропускаются — это не дефект.
Пара «в таблице `id`, в примере `ID`» схлопывается в один класс `case_mismatch`.

## Тестовый датасет

Связный мини-портал: сделки, лиды, контакты, компании, задачи, пользователи и
справочники. Все ссылки между сущностями резолвятся — `COMPANY_ID` сделки
находится через `crm.company.get`, стадия есть в `crm.status.list`, воронка —
в `crm.category.list`.

Даты скользящие: раскладываются относительно даты сборки, чтобы сценарии вроде
«сделки за последний месяц» не протухали. Поэтому датасет детерминирован в паре
(seed, дата сборки), а дата входит в версию — `dataset@v1+2026-08-14`. Датасет
генерируется на сборке, а не на старте сервиса: иначе одинаковая версия
означала бы разные данные.

## Локальная проверка

Сайт собирается `@diplodoc/cli`. Расширения из `extensions/` требуют, чтобы
CLI был доступен из корня репозитория:

```bash
npm install @diplodoc/cli
npx yfm -i . -o ../out
```

В версии CLI 5.x ресурсы из `.yfm` в собранные страницы не инжектятся —
на продакшене это работает, локально теги `<link>`/`<script>` нужно добавить
в `<head>` вручную.
